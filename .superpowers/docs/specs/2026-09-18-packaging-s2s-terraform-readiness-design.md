# Packaging S2S Terraform-Readiness Design

Date: 2026-09-18

## Summary

The Packaging service-to-service API is a thin interface over the existing
Packaging commands. A future Terraform provider can use its stable internal
resource IDs and project-scoped reads, but the current contract cannot safely
recover an ambiguous create, cannot distinguish configured recipe components
from mandatory components injected by VEW, and accepts component definitions as
opaque YAML while returning them as structured data.

This design hardens only the Packaging S2S API under
`/clients/packaging/v1`. It adds idempotent creates, makes component definitions
structured and symmetric, separates configured and effective recipe component
lists, and makes lifecycle polling guarantees explicit. The user-facing
Packaging API and UI remain unchanged.

The future Terraform provider will live in a dedicated
`terraform-provider-vew` repository. Building that provider is not part of this
change.

## Goals

- Make server-generated resource creation safe to retry after a lost response.
- Give automation a canonical, round-trippable component-definition model.
- Let declarative clients distinguish recipe intent from server-injected
  mandatory components.
- Specify deterministic polling and terminal-state behavior.
- Preserve all existing user-facing Packaging API behavior.
- Keep the S2S API consumer-neutral rather than adding Terraform-specific
  endpoints or persistence.

## Non-goals

- Implementing a Terraform provider.
- Starting image builds from Terraform.
- Changing the user-facing Packaging API or UI.
- Adding external resource IDs, name-based identity, or identity mappings.
- Adding an operation resource or general reconciliation engine.
- Adding ETags, pagination, or name filters in this change.
- Migrating every historical recipe version to reconstruct its original
  configured component list.

Image list and read endpoints remain available so a future provider can expose
images as data sources. `POST /images` remains outside the Terraform-ready
contract for now.

## Existing capabilities retained

The future provider can use the existing internal IDs as stable identities. No
API change is required for import. Conventional import strings can combine the
project and resource hierarchy:

```text
component:         <projectId>.<componentId>
component version: <projectId>.<componentId>.<versionId>
recipe:            <projectId>.<recipeId>
recipe version:    <projectId>.<recipeId>.<versionId>
pipeline:          <projectId>.<pipelineId>
```

The current OAuth client-credentials flow, project assignments, scope model,
direct reads by internal ID, stable problem codes, and resource status polling
also remain authoritative.

## Chosen approach

The changes extend the current S2S v1 routes and reuse the existing Packaging
domain commands and DynamoDB table.

Two broader alternatives were rejected:

1. A new declarative API with external IDs, `PUT` reconciliation, ETags, and
   operation resources would provide stronger general automation semantics but
   would duplicate the lifecycle model and exceed the provider-readiness goal.
2. Compensating entirely in the provider would leave ambiguous creates
   unrecoverable and would either create perpetual recipe drift or hide remote
   changes.

The S2S contract is still a proof of concept without external consumers, so its
component-definition and recipe-component request fields change directly in
v1. There is no dual-format transition period.

## API changes

### Idempotent create requests

The following endpoints require an `Idempotency-Key` header:

```text
POST /projects/{projectId}/components
POST /projects/{projectId}/components/{componentId}/versions
POST /projects/{projectId}/recipes
POST /projects/{projectId}/recipes/{recipeId}/versions
POST /projects/{projectId}/pipelines
```

The key is an RFC 4122 UUID generated by the caller. Missing or malformed keys
return `400 INVALID_IDEMPOTENCY_KEY`.

Keys are scoped by:

```text
(clientId, projectId, operation, parentResourceId?, idempotencyKey)
```

The same UUID may therefore be used for a different operation or project
without collision. The API applies request-model defaults and then serializes
the validated body as compact UTF-8 JSON with object keys sorted
lexicographically and array order preserved. It calculates a SHA-256 hash of
those bytes. Path identifiers and the operation are already part of the key
scope and are not duplicated in the request hash.

The behavior is:

- A new key is reserved atomically before the domain command runs.
- The reservation contains a pre-generated resource ID, so all attempts use the
  same domain identity.
- Repeating the key with the same canonical request returns the stored status
  and response body without creating another resource.
- Reusing the key within the same scope with a different request returns
  `409 IDEMPOTENCY_KEY_REUSED` with `retryable: false`.
- A request that finds a live attempt still running returns
  `409 IDEMPOTENCY_REQUEST_IN_PROGRESS`, `retryable: true`, and `Retry-After: 5`.
- Request parsing, schema validation, authentication, authorization, and project
  access checks occur before reservation. Failures at those boundaries do not
  consume a key.
- Deterministic domain rejections after reservation are recorded, so an exact
  retry receives the same stable problem code without re-running the command.
- Retryable infrastructure failures do not become permanent cached failures.
  They leave a recoverable reservation that can resume after its lease expires.

`POST /images` does not require an idempotency key in this change because image
creation is excluded from the initial Terraform scope. Its existing warning
about potentially billable duplicate builds remains in the API documentation.

### Idempotency persistence and recovery

Idempotency records live in the existing Packaging DynamoDB table. A record
contains:

```text
clientId
projectId
operation
parentResourceId
idempotencyKey
requestHash
generatedResourceId
status: IN_PROGRESS | COMPLETED
responseStatus
responseBody
leaseExpiresAt
expiresAt
createdAt
lastUpdateAt
```

Reservation uses a conditional write. Concurrent first requests for the same
scope and key cannot both acquire the record.

An `IN_PROGRESS` record has a 60-second lease. When the lease expires, a retry
checks the pre-generated resource ID through the appropriate query service:

- If the resource exists, the API reconstructs the successful create response,
  completes the idempotency record, and returns it.
- If the resource does not exist, the API may re-run the create command with the
  same pre-generated ID and acquire a new lease.

This recovery rule covers a process failure after the domain entity commits but
before the response or idempotency record is completed. Domain create commands
must therefore accept an injected ID for the S2S path. Other call sites may
continue using their existing generated defaults.

Completed records are retained for at least 24 hours. DynamoDB TTL removes them
eventually; application logic uses `expiresAt`, not physical deletion timing,
to decide whether a record is active.

### Structured component definitions

S2S component-version create and update requests replace the YAML string field:

```text
componentVersionYamlDefinition
```

with:

```text
componentVersionDefinition
```

The new field is a structured object matching the validated EC2 Image Builder
component document already produced by the read path:

```json
{
  "componentVersionDescription": "Installs the build agent",
  "componentVersionReleaseType": "MAJOR",
  "componentVersionDefinition": {
    "name": "Install build agent",
    "description": "Installs and validates the agent",
    "schemaVersion": "1.0",
    "constants": [],
    "parameters": [],
    "phases": [
      {
        "name": "build",
        "steps": [
          {
            "name": "InstallAgent",
            "action": "ExecuteBash",
            "timeoutSeconds": 300,
            "onFailure": "Abort",
            "maxAttempts": 1,
            "inputs": {
              "commands": [
                "apt-get update",
                "apt-get install -y example-agent"
              ]
            }
          }
        ]
      }
    ]
  },
  "softwareVendor": "Example Corp",
  "softwareVersion": "1.0.0"
}
```

The structured definition has these rules:

- `schemaVersion` and at least one phase are required.
- Phase names are `build`, `validate`, or `test`.
- Each phase contains an ordered, non-empty step list.
- Step `name` and `action` are required.
- `timeoutSeconds`, `onFailure`, and `maxAttempts` retain the current defaults
  and validation.
- Phase and step order is significant and is preserved.
- `inputs` is a JSON-compatible free-form object or array because its shape
  depends on the Image Builder action.
- Constants and parameters retain the existing AWS document structure.
- Unknown top-level and phase properties are rejected.

VEW validates and canonicalizes the object, serializes it to YAML, and then
uses the unchanged domain event and S3 definition workflows. Canonicalization
applies explicit defaults and preserves list order; it does not sort phase or
step lists.

The component-version `GET` response replaces `yaml_definition` and
`yaml_definition_b64` with a top-level `componentVersionDefinition` property
alongside the existing `component_version` representation. It returns the same
canonical structure accepted by create and update:

```json
{
  "component_version": {
    "componentId": "comp-example",
    "componentVersionId": "vers-example",
    "status": "VALIDATED"
  },
  "componentVersionDefinition": {
    "schemaVersion": "1.0",
    "phases": [
      {
        "name": "build",
        "steps": [
          {
            "name": "InstallAgent",
            "action": "ExecuteBash",
            "timeoutSeconds": 300,
            "onFailure": "Abort",
            "maxAttempts": 1,
            "inputs": {
              "commands": ["install-agent"]
            }
          }
        ]
      }
    ]
  }
}
```

The user-facing API continues accepting and returning YAML and base64 fields as
it does today.

### Configured and effective recipe components

The S2S recipe-version create and update request field becomes:

```text
configuredComponentsVersions
```

It contains only component versions explicitly selected by the caller. The
domain workflow continues to prepend and append mandatory components according
to the recipe platform, architecture, and operating-system version.

Recipe-version reads expose both views:

```json
{
  "recipe_version": {
    "recipeId": "reci-example",
    "recipeVersionId": "vers-example",
    "configuredComponentsVersions": [
      {
        "componentId": "comp-user",
        "componentName": "user-component",
        "componentVersionId": "vers-user",
        "componentVersionName": "1.0.0",
        "componentVersionType": "MAIN",
        "order": 1
      }
    ],
    "effectiveComponentsVersions": [
      {
        "componentId": "comp-mandatory",
        "componentName": "mandatory-helper",
        "componentVersionId": "vers-mandatory",
        "componentVersionName": "1.0.0",
        "componentVersionType": "HELPER",
        "order": 1
      },
      {
        "componentId": "comp-user",
        "componentName": "user-component",
        "componentVersionId": "vers-user",
        "componentVersionName": "1.0.0",
        "componentVersionType": "MAIN",
        "order": 2
      }
    ]
  }
}
```

`configuredComponentsVersions` is persisted before mandatory components are
injected. The existing internal `recipeComponentsVersions` field remains the
effective ordered list used by the recipe, testing, and image-building domain
workflows. The S2S response maps that internal list to
`effectiveComponentsVersions`.

All recipe-version create and update command paths persist the configured list,
including commands initiated by the user API. This does not change the user API
payload; it prevents the S2S view becoming stale if a version is later edited
through the UI.

Historical recipe versions may lack the new configured field. Their S2S reads
omit `configuredComponentsVersions` and still return
`effectiveComponentsVersions`. The API does not guess historical intent by
subtracting today's mandatory list. Updating a historical version through any
supported path records its configured list from that point forward.

### Explicit lifecycle contract

The API continues polling resources directly and does not add operation
resources.

Synchronous behavior is:

- Component and recipe creation return `201 Created`.
- Component update and base-resource archive return `200 OK`.
- Component-version and recipe-version release return `200 OK`; the resource is
  already `RELEASED` when the response is returned.
- Repeating archive, retirement, or release succeeds when the resource is
  already in the requested terminal state.

Asynchronous component-version create, update, and retirement; recipe-version
create, update, and retirement; and pipeline create, update, and retirement
return:

```http
HTTP/1.1 202 Accepted
Retry-After: 5
Content-Type: application/json
```

The body contains the affected resource ID as it does today.

OpenAPI replaces unconstrained lifecycle strings with these enums:

```text
ComponentStatus:
  CREATED, ARCHIVED

ComponentVersionStatus:
  CREATING, CREATED, TESTING, VALIDATED, UPDATING, RELEASED, RETIRED, FAILED

RecipeStatus:
  CREATED, ARCHIVED

RecipeVersionStatus:
  CREATING, CREATED, TESTING, VALIDATED, UPDATING, RELEASED, RETIRED, FAILED

PipelineStatus:
  CREATING, CREATED, UPDATING, RETIRED, FAILED

ImageStatus:
  CREATING, CREATED, RETIRED, DELETED, FAILED
```

Polling guarantees are:

- A successful create is immediately addressable by ID even while asynchronous
  work continues.
- Direct reads remain available for archived and retired resources.
- Terminal states do not regress.
- Temporary read propagation failures use a distinct retryable problem code;
  they are not returned as an indistinguishable permanent `404`.
- The API documentation names the expected success and failure terminal states
  for every asynchronous mutation.

An immediate request failure continues using `application/problem+json` with a
stable `code`, `requestId`, and `retryable`. A successful read whose resource has
reached `FAILED` remains a resource representation rather than becoming an HTTP
error. Persisting additional workflow failure diagnostics is outside this
change.

## Endpoint impact summary

| Endpoint family | Change |
| --- | --- |
| Component create | Require `Idempotency-Key`; pre-generate the component ID |
| Component-version create | Require `Idempotency-Key`; accept a structured definition; pre-generate the version ID |
| Component-version update | Accept a structured definition |
| Component-version read | Return the structured definition; remove S2S YAML/base64 fields |
| Recipe create | Require `Idempotency-Key`; pre-generate the recipe ID |
| Recipe-version create | Require `Idempotency-Key`; accept configured components; pre-generate the version ID |
| Recipe-version update | Accept and persist configured components |
| Recipe-version read | Return configured and effective components when configured state is available |
| Pipeline create | Require `Idempotency-Key`; pre-generate the pipeline ID |
| Version/pipeline async mutations | Enumerate states and guarantee `Retry-After` |
| Image list/read | No behavioral change; suitable for a future data source |
| Image create | No change; explicitly outside the initial Terraform contract |

## Component boundaries

### S2S routers

The routers own header validation, request-model validation, authorization,
idempotency orchestration, response replay, and S2S response mapping. They do
not duplicate Packaging lifecycle validation.

### Idempotency service

A Packaging S2S idempotency service owns conditional reservation, canonical
request hashing, leases, replay, and expiry. Resource-specific router callbacks
provide ID generation, existence checks, command dispatch, and response
construction. Keeping these callbacks narrow avoids coupling the generic state
machine to every domain model.

### Domain commands and models

Create commands accept optional pre-generated IDs. Existing user-initiated call
sites retain default ID generation. Recipe-version create and update handlers
persist the configured list before producing the existing effective list.

Component-definition domain events and storage continue carrying serialized
YAML so the user API and downstream AWS integration do not change.

### Query and response mapping

Query services continue returning domain resources by internal ID. The S2S read
mapper parses stored component YAML into the structured contract and maps the
two recipe component views. Parsing a stored definition that cannot satisfy the
contract returns a stable server problem and emits an operational alert; it
must not silently return a different definition.

## Data flows

### Create with idempotency

1. API Gateway authenticates the client and checks the route scope.
2. The router validates the path, body, project assignment, and key syntax.
3. The idempotency service canonicalizes and hashes the body.
4. A conditional write reserves the scoped key with a generated resource ID.
5. The router dispatches the existing domain command with that ID.
6. The API completes the idempotency record with the success status and body.
7. The response is returned.
8. An exact retry replays step 7 without dispatching another command.

### Structured component definition

1. The S2S request model validates the structured document.
2. The adapter applies defaults and serializes canonical YAML.
3. Existing component-version commands, events, and S3 services process that
   YAML unchanged.
4. A read loads the stored bytes, parses and validates them, and returns the
   canonical object.

### Recipe component views

1. The caller submits `configuredComponentsVersions`.
2. The command handler validates and saves that ordered list.
3. Existing mandatory-component logic builds the effective list.
4. Existing workflows consume the effective list.
5. The S2S read mapper exposes both lists without asking the client to manage
   mandatory entries.

## Error contract

New stable problem codes are:

| HTTP status | Code | Retryable | Meaning |
| --- | --- | --- | --- |
| `400` | `INVALID_IDEMPOTENCY_KEY` | false | Header missing or not a valid UUID |
| `409` | `IDEMPOTENCY_KEY_REUSED` | false | Same scoped key used with a different canonical request |
| `409` | `IDEMPOTENCY_REQUEST_IN_PROGRESS` | true | Matching request owns a live lease |
| `422` | `INVALID_COMPONENT_DEFINITION` | false | Structured component definition violates the document contract |
| `503` | `RESOURCE_READ_NOT_READY` | true | A newly accepted resource is temporarily not readable |

Existing authorization and project-isolation behavior remains unchanged. A
client without project access receives `403 PROJECT_ACCESS_DENIED` before
resource existence is disclosed.

## Security

- Idempotency records store a request hash, not bearer tokens or client
  credentials.
- Logs never contain bearer tokens, client secrets, component command bodies,
  or complete component definitions.
- Idempotency scope includes the authenticated client ID, preventing one client
  from observing or replaying another client's response.
- Stored error bodies contain only the same safe details allowed by the public
  problem contract.
- Component definitions remain subject to the existing domain and Image Builder
  validation; structuring the transport does not make arbitrary commands safe
  to execute.

## Observability

Structured logs include operation, project ID, client ID, a one-way hash of the
idempotency key, generated resource ID, and replay outcome.

Metrics cover:

- new idempotency reservations;
- successful replays;
- key reuse conflicts;
- requests blocked by an active lease;
- expired-lease recoveries;
- completed-record expiry;
- structured-definition validation failures; and
- failures parsing stored definitions.

The normal request ID is retained on every transport response. Replayed success
bodies remain identical, but logs distinguish the original execution from the
new transport request.

## Compatibility and rollout

This change intentionally breaks only the Packaging S2S v1 request and response
schema. The S2S API is still a proof of concept without external consumers.

Deployment consists of:

1. Add optional persistence fields and idempotency record support.
2. Update domain create commands to accept injected IDs while retaining their
   existing defaults.
3. Update recipe handlers to retain configured lists.
4. Update S2S request models, routers, response mappers, and OpenAPI.
5. Regenerate the S2S models.
6. Update the Bruno S2S collection and `docs/packaging-s2s-api.md`.
7. Deploy the backend and contract together.

No table migration is required. Existing resources keep their IDs and remain
readable. Historical recipe versions omit their unavailable configured list.

## Testing

### Idempotency

- Two concurrent requests using the same key and body create one resource.
- Retrying after a simulated lost response returns the original resource ID.
- Recovery after a simulated commit-before-completion failure finds the
  pre-generated ID and completes the record.
- An expired reservation with no resource safely retries using the same ID.
- Reusing a key with a different body returns
  `IDEMPOTENCY_KEY_REUSED`.
- A live attempt returns `IDEMPOTENCY_REQUEST_IN_PROGRESS` and `Retry-After`.
- Invalid, unauthorized, and project-denied requests do not reserve keys.
- Completed records obey logical expiry independently of delayed DynamoDB TTL
  deletion.

### Structured component definitions

- Create, storage, and read round-trip without semantic change.
- Phase and step ordering is preserved.
- Defaults are applied consistently.
- Invalid phase names, empty step lists, invalid step fields, and unknown
  top-level or phase properties are rejected.
- Action-specific `inputs` objects and arrays survive serialization.
- Existing user API YAML and base64 responses remain unchanged.

### Recipe component views

- Create and update preserve the submitted configured order.
- Effective output includes mandatory prepend and append components in domain
  order.
- The configured list never contains server-injected entries.
- A version updated through the user API refreshes its configured metadata.
- A legacy version remains readable and omits the unavailable configured list.

### Lifecycle and contract

- Every asynchronous mutation returns `202` and `Retry-After`.
- Release returns only after the resource is `RELEASED`.
- Repeated archive, retirement, and release requests succeed at their target
  state.
- Archived and retired resources remain directly readable.
- OpenAPI status enums match the domain enums.
- OpenAPI, generated models, router behavior, Bruno examples, and narrative
  documentation agree.
- Existing Packaging S2S and user API suites continue to pass.

## Future provider boundary

The future provider can build on this contract with managed resources for
components, component versions, recipes, recipe versions, and pipelines, plus
image data sources. It can use composite import identities based on the current
internal IDs. Component definitions can map to nested phase and step sections,
while action-dependent `inputs` remain a dynamic JSON-compatible value.

Image creation, provider actions, ETags, inventory pagination, name-based data
sources, and broader VEW resources require separate designs.
